# Project Architecture

Phase 2 adds a tenant-scoped salon profile and physical branches. Flutter and web clients will consume `/api/v1`; neither will access MySQL directly. The application uses controllers, Form Requests, Resources, policies, and application support services. Payments and subscriptions were deliberately not added until Phase 10 (see below), once the product had a real business (bookings, staff, customers) worth billing for.

`User` is the unified identity. `Tenant` represents a salon business. The `tenant_user` pivot allows one user to have memberships in multiple tenants with a tenant-specific role.

Each tenant has one `Salon` profile and zero or more `Branch` records. A salon owns settings; a branch owns working hours and holidays.

Phase 3 adds tenant-scoped, branch-specific service categories and services. Each branch owns its service price, duration, status, and future availability configuration.

Phase 4 adds staff profiles, optionally linked to an existing tenant-staff `User` login, with many-to-many branch and service assignments plus individual working hours, breaks, and leave. See `STAFF_ARCHITECTURE.md`.

Phase 5 adds tenant-scoped customer profiles, optionally linked to a platform `User` (role `customer`), with tenant-scoped phone uniqueness, owner-managed internal notes, and self-service profile endpoints outside `tenant.context`. See `CUSTOMER_ARCHITECTURE.md`.

Phase 6 adds the appointment booking engine: multi-service, multi-staff bookings with item-level price/duration snapshots, a reusable availability/slot-generation service, transactional lock-based double-booking prevention, cancellation/reschedule with full server-side revalidation, and a status-transition audit trail. See `BOOKING_ENGINE.md`.

Phase 7 adds the Flutter **customer** mobile app (`mobile/`, Android + iOS from one codebase) consuming `/api/v1` exactly as Phases 1–6 defined it, plus two small additive backend endpoints the customer app genuinely needed and Phases 1–6 never exposed to a non-tenant-member customer (`GET /customer/salons`, `GET /branches/{branch}/services`) and one additive field on the availability response (`staff` names). See `FLUTTER_ARCHITECTURE.md`, `FLUTTER_SETUP.md`, and `MOBILE_API_INTEGRATION.md`.

Phase 8 extends that same Flutter project — never a second app — with a role-aware owner/admin surface consuming the existing Phase 2–6 tenant-management APIs (`/staff*`, `/customers*`, `/services*`, `/service-categories*`, `/branches*`, `/salon*`, `/bookings*`) plus one new additive endpoint, `GET /dashboard/summary`, aggregating today's booking counts, revenue, next appointment, staff availability, and customer counts from real data. The Phase 5 `CustomerController::summary` endpoint, previously a placeholder returning zeros, now derives real totals from booking history. Which surface a session sees is decided client-side from `UserResource.role` (`customer` / `salon_owner` / `super_admin` / `staff`) purely for navigation; every request is still independently authorized server-side by the same tenant-management policies Phases 2–6 already enforce, regardless of which screen requested it. See `OWNER_APP_ARCHITECTURE.md`.

Phase 9 extends the same project a third time with a real staff surface at `/staff` (replacing Phase 8's `staff`-role placeholder), reusing the owner surface's booking/staff repositories wherever the backend already authorizes staff identically to an owner (every `BookingController` action is `viewableTenant()`-gated — staff already had full tenant-wide booking access since Phase 6, unchanged here) and showing schedule/services/leave/profile as view-only wherever the backend restricts writes to `managedTenant()` (owner/super-admin only). Exactly one new backend endpoint was added, `GET /staff/me`, resolving the authenticated user's own staff profile server-side rather than trusting a client-supplied staff id — mirroring the Phase 5 `GET /customer/profile` self-resolution pattern. See `STAFF_APP_ARCHITECTURE.md`.

Phase 10 adds SaaS billing: platform-global `plans` (database-driven, never hard-coded — the default `SALON_BASIC` is ₹500.00/month with a 14-day trial), a one-row-per-tenant `subscriptions` table with a real state machine, `payments`/`invoices`/`invoice_items` with atomically-generated sequential invoice numbers and price-at-billing-time snapshots, and a `PaymentGatewayInterface`-abstracted Razorpay integration where payments are verified server-side and never trusted from the client. Every tenant automatically starts a trial the instant it's created (`Tenant::booted()`), so this required no change to Phase 1's registration flow or any Phase 1–9 test. A new `EnsureActiveSubscription` middleware gates the existing Phase 2–6 business routes (never the billing routes themselves) on subscription standing. See `SAAS_BILLING_ARCHITECTURE.md`.

Phase 11 adds a multi-channel notification system (in-app, push, email, WhatsApp, SMS) behind one `NotificationDispatcher`, reused by Phase 12 without modification. See `NOTIFICATION_ARCHITECTURE.md`.

Phase 12 adds coupons, paid customer memberships, and a loyalty points program — one `BookingPricingService` (coupon-or-membership-benefit, plus optional loyalty redemption) that `BookingService::create()` calls from inside its existing transaction, so every discount is server-computed and permanently snapshotted onto the booking. Customer memberships get their own payment ledger reusing Phase 10's exact `PaymentGatewayInterface`/webhook — deliberately never conflated with the SaaS subscription domain, a completely different concept (owner pays platform vs. customer pays salon). See `LOYALTY_MEMBERSHIP_COUPON_ARCHITECTURE.md`.

Phase 13 adds owner-only reports and analytics — ten `GET /reports/*` endpoints, each backed by one `App\Services\Reports\*Report` class (revenue, bookings, customers, services, staff, branches, coupons, memberships, loyalty, plus a date-range-flexible dashboard) that aggregates entirely in SQL over real Phase 1–12 data; no controller performs its own aggregation. A shared `DateRange`/`ReportTimezoneResolver` pair resolves every "today"/"this month" boundary against the salon's or a filtered branch's own timezone rather than the server's default — a bug this phase also fixed in Phase 8's `GET /dashboard/summary`, which had been using the server's UTC clock. Revenue/staff/service attribution reads `booking_items`' historical price snapshots (never a service's current price) and proportionally allocates each booking's single `discount` value across its items, so a later price or coupon-config change never rewrites a past report. See `REPORTING_ANALYTICS_ARCHITECTURE.md`.

Phase 14 is a security + performance hardening pass across Phases 1–13 — no new feature surface. A full code audit (not assumption-based) found no CRITICAL/HIGH issues, and fixed several real MEDIUM ones: two MySQL-specific race conditions invisible under the SQLite test suite (a booking staff-conflict check and a coupon per-customer usage check both upgraded from plain reads to locking reads once already inside a lock-holding transaction), a webhook-idempotency gap that could permanently swallow a crashed delivery, checkout no longer holding a DB transaction open across the synchronous Razorpay HTTP call, a previously-absent general API rate limit, and an inconsistent cascade-delete on customer-linked loyalty/membership tables corrected to match the project's own established `restrictOnDelete()` convention for financial history. See `SECURITY_HARDENING.md` and `PERFORMANCE_HARDENING.md` for the full audit, including everything reviewed and confirmed already correct.

A gap surfaced during real-device testing after Phase 15's production deployment, not part of the original numbered phase sequence: there was no way for a new person to actually become a salon owner. `POST /api/v1/auth/register` (Phase 1) always creates a `customer`, and no controller anywhere created a `Tenant` — every tenant in the system had come from a seeder or test fixture, a fact `Tenant::booted()`'s own code comment already documented. `App\Services\Auth\OwnerRegistrationService` closes this: one new endpoint, `POST /auth/register-owner`, creates the owner's `User` (role hardcoded server-side, exactly like the customer path hardcodes `CUSTOMER`), a new `Tenant`, and the `tenant_user` owner membership, all in one transaction — `Tenant::booted()`'s existing trial-start hook fires automatically, unmodified. The customer registration endpoint, its contract, and its tests are completely untouched. See `MOBILE_API_INTEGRATION.md`, "Self-service salon-owner registration", and `API_DOCUMENTATION.md`, "Owner onboarding".

Further real-device testing against that new registration flow surfaced a second, related gap: a freshly-registered owner has a `Tenant` but deliberately no `Salon` yet (a separate onboarding step), and `BranchController::store()` assumed one already existed, throwing a raw `ModelNotFoundException` on a new owner's very first "Add branch" attempt instead of a clean business error. Fixed with a new `TenantManagementController::requireSalon()` helper (a tenant-scoped `Salon::query()->first()`, never a global lookup, returning a normal `422` when none exists) plus matching Flutter changes — a post-registration redirect to Salon setup, a dashboard setup-prompt safety net, and a `SalonProfileScreen` that can now create a first salon, not just edit one. See `OWNER_APP_ARCHITECTURE.md` and `FLUTTER_ARCHITECTURE.md`, both "Owner onboarding: salon setup", and `API_DOCUMENTATION.md`, "Setup-completion gap (fixed)".

A targeted feature addition, not a new phase: Service Media & Instagram Reference lets an owner attach an image, a description (already existed since Phase 3), and an optional Instagram post/reel/video URL to a service, so a customer sees real photos/descriptions and can open the real Instagram post from the booking flow. Only one column was new (`services.instagram_url`) — `description` and `image` already existed; the real fix was that `ServiceResource` had always returned the raw internal storage path under `image`, never a URL any client could actually load, corrected to a proper `image_url` (`Storage::disk('public')->url(...)`, or `null`). `App\Support\InstagramUrl` validates/normalizes the URL (must be `https://instagram.com/(p|reel|tv)/...`; a `javascript:`/non-Instagram URL is rejected with a normal `422`; nothing is ever downloaded, scraped, or thumbnailed from Instagram). Replacing or removing an image now deletes the old file from storage instead of orphaning it; a soft-deleted service keeps its image (recoverable), and only a genuine `forceDelete()` — no code path calls this today — cleans it up, via a new `Service::booted()` hook. Booking pricing, availability, staff assignment, coupons, memberships, and loyalty are all untouched — service selection during booking still uses the same service id it always did. See `API_DOCUMENTATION.md`, "Service media"; `OWNER_APP_ARCHITECTURE.md` and `FLUTTER_ARCHITECTURE.md`, both "Service media".

A second, smaller targeted addition on top of that one: the salon itself (not any individual service) can now carry its own official Instagram profile link — `salons.instagram_url`, the only new column, added to the existing `salons` table (the tenant's one business-profile row) rather than duplicated anywhere else. It reuses the same `App\Support\InstagramUrl` validation/normalization class Service Media introduced, through a second method (`isValidProfile()`) that accepts a bare username path and rejects the `/p/`/`/reel/`/`/tv/` shapes the service field requires — the two fields are validated differently on purpose and are never interchangeable: a salon has one profile; a service can separately reference one specific post/reel. Reused the existing Salon Profile screen and `/salon` API entirely — no new endpoint, no new screen. See `API_DOCUMENTATION.md`, "Salon Instagram profile"; `OWNER_APP_ARCHITECTURE.md` and `FLUTTER_ARCHITECTURE.md`, both "Salon Instagram profile".

A larger targeted addition on top of both: **Master Catalog & Service Segmentation**, making the SaaS ready-to-use for a non-technical owner. A new tenant no longer starts with an empty service list — the first time a tenant creates a branch, `CatalogProvisioningService` copies a curated, platform-level starting catalog (new tables `master_service_categories`/`master_services`, seeder-managed only, never tenant-owned and never directly reachable by any API route) into that tenant's own `service_categories`/`services` — a one-time copy, never a live link, so editing a provisioned service afterward can never affect the master catalog or any other tenant. A new `App\Enums\ServiceAudience` (`male`/`female`/`unisex`/`kids`) — deliberately its own enum, not a reuse of `GenderType` — classifies both the master catalog and tenant services/categories, and drives a new customer-app screen ("What service are you looking for?" — Men/Women/Unisex/Kids) inserted between the existing branch-selection and service-catalog screens, plus a matching audience filter on the owner's Services screen alongside a quick per-service ON/OFF toggle. Booking pricing, availability, staff assignment, tenant isolation, and every existing authorization rule are unchanged — a provisioned service is, from the moment it's created, an ordinary tenant-owned `Service` row indistinguishable from one an owner typed in by hand. See `MASTER_CATALOG_ARCHITECTURE.md` for the full design.
