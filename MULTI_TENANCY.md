# Multi-tenancy

This project uses shared-database, row-level tenancy. The authenticated user is the authority for membership; a body `tenant_id` is never trusted.

`ResolveTenantContext` chooses the user's active tenant membership, or an `X-Tenant-Slug` only after verifying that the user belongs to that active tenant. It stores the result in request-scoped `TenantContext` and clears it after the response. Future public routes can resolve by slug or subdomain without changing tenant-owned models.

Tenant routes must use `auth:sanctum` and the `tenant.context` middleware alias.

Tenant-owned models must use `App\Models\Concerns\BelongsToTenant`. The trait scopes queries to the context, fails closed when no context exists, and overwrites `tenant_id` during creation. Platform tables must not use this trait. Platform-wide reporting must deliberately opt out of the global scope from a reviewed platform-only service.

`Salon`, `SalonSetting`, `Branch`, `BranchWorkingHour`, and `BranchHoliday` are tenant-owned. Controllers do not accept tenant IDs or salon IDs from branch clients: tenant IDs come from the context and a branch is attached to the current tenant's salon. Direct branch and holiday IDs are resolved through scoped queries, so another tenant receives a 404 rather than data.

Service categories and services use the same scope. The API validates branch and category ownership in the current tenant context, including that a category belongs to the selected branch.

`Staff`, `StaffWorkingHour`, `StaffBreak`, and `StaffLeave` are tenant-owned via `BelongsToTenant`. `staff_branches` and `staff_services` are tenant-owned pivot tables; because bulk pivot writes (`sync()`/`attach()`) do not fire the `creating` model event that `BelongsToTenant` relies on, controllers set `tenant_id` explicitly on each pivot row rather than trusting an implicit default. Staff, branch, and service IDs supplied by clients are always re-validated against the current tenant context in the relevant Form Request; a foreign-tenant ID resolves to a validation error or a 404, never a cross-tenant write.

`Customer` and `CustomerNote` are tenant-owned via `BelongsToTenant`, following the same pattern. Customers are deliberately **not** `tenant_user` members — `TenantMembershipRole` remains `salon_owner`/`staff` only, so a customer can never pass `ResolveTenantContext`'s membership check and therefore can never reach a `tenant.context` route, including tenant configuration. `TenantManagementController` gained an additive `viewableTenant()` helper alongside the existing `managedTenant()`, both still built on `TenantContext::require()` plus a `Gate::authorize()` call — `viewableTenant()` authorizes via the existing `TenantPolicy::view` (any tenant member: owner or staff) where `managedTenant()` authorizes via `TenantPolicy::manage` (owner/super admin only); no policy classes changed. The one deliberate, reviewed `BelongsToTenant` scope bypass in this phase is `CustomerProfileController`, which resolves a customer's own profile by `user_id = auth()->id()` across tenants (needed because a customer may have profiles in more than one tenant and cannot supply a tenant context) — every such query is still constrained to the authenticated user's own rows, so it cannot leak another user's data.

`Booking`, `BookingItem`, and `BookingStatusHistory` (Phase 6) are tenant-owned via `BelongsToTenant`; see `BOOKING_ENGINE.md` for the full booking architecture. `BookingController` uses `viewableTenant()` for every action (not just reads) — staff get the same full operational access as owner on bookings specifically, a deliberate broadening documented in `BOOKING_ENGINE.md`. The availability endpoint (`GET /branches/{branch}/availability`) and the customer booking self-service surface (`/customer/bookings*`) both run outside `tenant.context`, following the same reviewed scope-bypass pattern as `/customer/profile`: they resolve the relevant tenant directly (from the branch ID, or from the caller's own `customer_profiles` rows) rather than requiring a `tenant_user` membership. `AvailabilityRequest`, which validates before the controller can set `TenantContext`, is the one place that must bypass *two* scopes explicitly — `Branch` and, when loading its settings, `SalonSetting` — since an eager-loaded relation still applies its own model's global scope even when the root query bypassed its own.

Phase 7 (the Flutter customer app) added two more endpoints on this same "no `tenant_user` membership" side of the boundary, both read-only: `GET /branches/{branch}/services` (resolves tenant from the branch id, same as availability) and `GET /customer/salons` (resolves every tenant from the caller's own `customer_profiles` rows, same `user_id`-constrained bypass pattern as `/customer/profile` — see `MOBILE_API_INTEGRATION.md`). Neither accepts a tenant/customer ID from the client; both derive it entirely from the authenticated session's own data.

`Subscription`, `Payment`, `Invoice`, and `InvoiceItem` (Phase 10) are tenant-owned via `BelongsToTenant`, following the same pattern as every table above — a cross-tenant `findOrFail()` on a payment/invoice id 404s exactly like a cross-tenant staff or booking id always has. `Plan` is deliberately **not** tenant-owned (no `BelongsToTenant`, no `tenant_id` column) — it's platform-global, the same category as `Tenant` itself; every tenant reads the same plan rows. `WebhookEvent` and the `invoice_number_counters` single-row table are also platform-global for the same reason `webhook_events` needs to be: an inbound gateway webhook arrives with no authenticated tenant session at all, so there's no `TenantContext` to scope it by.

Two more reviewed, intentional `BelongsToTenant` scope bypasses were added this phase, both using the same `withoutGlobalScope('tenant')` pattern `CustomerBookingController` already established: `PaymentWebhookController` looks up a `Payment` by `gateway_order_id` across every tenant (the only way to route an inbound webhook to the right tenant at all — it then sets `TenantContext` to that payment's own tenant before doing anything further, so every subsequent write is correctly scoped), and `SubscriptionService::processLifecycle()` (the daily scheduler command) queries `Subscription` platform-wide since a console command has no authenticated tenant session either. Neither accepts a tenant ID from a client request; both derive their tenant strictly from data already in the database.

`EnsureActiveSubscription` (alias `subscription.active`, Phase 10) is a new middleware appended to the existing business-route group (branches, services, staff, customers, bookings, dashboard) — it reads the current tenant's subscription status from `TenantContext` (already resolved by `tenant.context`, which runs first) and blocks the request with `402` if the subscription isn't in an access-allowed state. It is deliberately **not** applied to the `/subscription*` billing routes themselves. See `SAAS_BILLING_ARCHITECTURE.md`, "Subscription access control", for the full policy.

Phase 12's coupons/membership plans/customer memberships/loyalty accounts all use the same `BelongsToTenant` trait, so cross-tenant direct-ID access 404s the same structural way every other tenant-owned model has since Phase 1 — no new scope-bypass pattern was introduced. `MembershipService`/`LoyaltyService`, which run from queued listeners and scheduler commands with no request-scoped `TenantContext`, follow the exact `save-then-restore` pattern (never an unconditional `clear()`) `SubscriptionService::startTrialFor()` established, so a listener never wipes out an outer request's tenant context mid-flight. See `LOYALTY_MEMBERSHIP_COUPON_ARCHITECTURE.md`.

The master service catalog (targeted addition, `master_service_categories`/`master_services`) is platform-global, deliberately **not** `BelongsToTenant` — the same category as `Plan`: every tenant reads from the same rows during provisioning, and no tenant ever writes to them (there is no HTTP route to either table at all). `CatalogProvisioningService::provisionForBranch()` copies master rows into a tenant's own `service_categories`/`services` exactly once per tenant (guarded by checking whether the calling tenant already has any `Service` with a non-null `master_service_id` — a check that is itself automatically tenant-scoped, since `Service` carries `BelongsToTenant`) — after that copy, the tenant's rows are ordinary `BelongsToTenant` data indistinguishable from anything an owner typed in by hand, so every existing tenant-isolation guarantee for `services`/`service_categories` applies to them unchanged. The two new columns this feature adds to those tables (`audience`, and `services.master_service_id`) are plain nullable columns, not new scope-bypass points. See `MASTER_CATALOG_ARCHITECTURE.md`.

Phase 14 re-audited every `BelongsToTenant`-eligible model (all 35 checked individually) and every controller's authorization call, and found the tenant-isolation architecture described above to still hold with no regressions: no model with a `tenant_id` column is missing the trait without a specifically-reviewed reason, no controller mutates data via `$request->all()` (bypassing FormRequest-level tenant-scoped `Rule::exists` validation), and every FormRequest that accepts a foreign-tenant-owned ID (`branch_id`, `staff_id`, `service_id`, `customer_id`, `coupon_id`, `membership_plan_id`, and every Phase 13 report filter) still validates it with `Rule::exists(...)->where('tenant_id', $currentTenantId)`. See "Tenant isolation" and "Cross-tenant relationship attacks" in `SECURITY_HARDENING.md` for the full re-audit.
