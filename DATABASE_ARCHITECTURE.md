# Database Architecture

Current tables include `users`, `tenants`, `tenant_user`, `salons`, `salon_settings`, `branches`, `branch_working_hours`, `branch_holidays`, `service_categories`, `services`, `staff_profiles`, `staff_branches`, `staff_services`, `staff_working_hours`, `staff_breaks`, `staff_leaves`, `customer_profiles`, `customer_notes`, `bookings`, `booking_items`, `booking_status_histories`, `plans`, `subscriptions`, `payments`, `invoices`, `invoice_items`, `webhook_events`, `invoice_number_counters`, `personal_access_tokens`, and Laravel cache/job/session/password-reset tables.

`tenants.id` is a ULID to avoid exposing sequential tenant identifiers. `tenant_user` has a composite primary key of `(tenant_id, user_id)`, a tenant-role column, and a reverse `(user_id, tenant_id)` index. Tenant-owned tables added in later phases must include `tenant_id`, foreign keys, and indexes based on actual tenant query paths.

`salons` has a unique tenant foreign key, enforcing one salon profile per tenant. Branch slugs are unique per tenant. Working hours are unique per `(branch_id, day_of_week)`; holidays are unique per `(branch_id, holiday_date)`. Branches and salons use soft deletes. All Phase 2 operational tables carry `tenant_id` and tenant/parent indexes.

`service_categories` and `services` are soft-deletable tenant-owned branch records. Service prices use `decimal(12,2)` and duration uses integer minutes. Indexes support branch/status, category, and gender filters.

`staff_profiles` is a soft-deletable tenant-owned record with a nullable, tenant-unique `user_id` foreign key. `staff_branches` and `staff_services` are tenant-owned pivot tables (`(staff_id, branch_id)` and `(staff_id, service_id)` unique) linking staff to branches and services; `tenant_id` is written explicitly on these pivot rows because `sync()`/`attach()` bypass Eloquent's `creating` model event. `staff_working_hours` is unique per `(staff_id, day_of_week)`, mirroring `branch_working_hours`. `staff_breaks` allows multiple rows per `(staff_id, day_of_week)`. `staff_leaves` indexes `(tenant_id, staff_id, start_date, end_date)` for future booking-engine leave lookups. None of the Phase 4 nested tables (working hours, breaks, leave, pivots) use soft deletes, matching `branch_working_hours`/`branch_holidays`; `staff_profiles` itself does, matching `branches`/`services`.

`customer_profiles` is a soft-deletable tenant-owned record with a nullable, tenant-unique `user_id` foreign key (mirroring `staff_profiles`, but with no `tenant_user`-style membership behind it — see `CUSTOMER_ARCHITECTURE.md`). It has no `branch_id`: a customer is not bound to a single branch. `phone`/`country_code` hold the display value; a computed `normalized_phone` (digits only, country code prefixed) is unique per `(tenant_id, normalized_phone)` and indexed for search. Additional indexes cover `(tenant_id, status)`, `(tenant_id, name)`, and `(tenant_id, email)` for the list/search/filter query paths. `customer_notes` is a separate, non-soft-deletable tenant-owned table (one row per note, `(tenant_id, customer_id)` indexed) rather than a profile column, since the API exposes it as a full CRUD sub-resource.

`bookings` (ULID, no soft delete — cancellation is a status, never a row deletion) carries `booking_date`/`start_time`/`end_time` as branch-local naive wall-clock values (see `BOOKING_ENGINE.md` for the timezone strategy), a `restrictOnDelete` foreign key to `customer_profiles` (protects booking history from a hard customer delete), and indexes on `(tenant_id, branch_id, booking_date)`, `(tenant_id, customer_id)`, `(tenant_id, status)`, and `(branch_id, booking_date, status)` for the availability and list/filter query paths. `booking_items` (auto-increment id, tenant-owned) snapshots `service_name`/`service_price`/`service_duration_minutes` independent of the current `Service` row, has a `restrictOnDelete` foreign key to `staff_profiles`, and indexes `(tenant_id, booking_id)` and `(tenant_id, staff_id)` — the latter backing the staff-conflict overlap query used by both slot generation and booking creation. `booking_status_histories` (auto-increment id, tenant-owned, append-only) indexes `(tenant_id, booking_id)`.

## Phase 10 — SaaS billing

`plans` (ULID, platform-global — no `tenant_id` at all, the only tenant-adjacent table in the schema that isn't tenant-scoped) holds `amount decimal(12,2)` matching every other money column in this schema, `code` unique, and an `is_active` flag indexed for the tenant-facing plan list query. The default row (`SALON_BASIC`, ₹500.00/month, 14-day trial) is inserted directly in the migration that creates the table, not only in `DatabaseSeeder` — see `SAAS_BILLING_ARCHITECTURE.md` for why that matters (every tenant, including ones created by a Phase 1–9 test fixture, gets a real trial subscription against a real plan row, in every environment).

`subscriptions` (ULID, tenant-owned) has a **unique** `tenant_id` — exactly one subscription row per tenant, mutated across its whole lifecycle rather than superseded by new rows on renewal. Indexes on `status` and `gateway_subscription_id` support the scheduler's lifecycle queries and gateway webhook lookups respectively. `grace_ends_at` is not in the original Phase 10 brief's suggested column list — added because the `PAST_DUE`/`GRACE_PERIOD` states need a concrete end-of-grace instant to transition on.

`invoices` (ULID, tenant-owned) has a unique `invoice_number` (format `INV-{year}-{6-digit sequence}`, reserved atomically via `invoice_number_counters` — a single locked row, not an auto-increment column, so the number can be reserved inside the same transaction that creates the invoice) and `(tenant_id, status)`/`subscription_id` indexes. `invoice_items` (auto-increment id, tenant-owned, mirroring `booking_items`' shape) snapshots `description`/`unit_amount` at billing time — never a live join to `plans` — so a later plan price change never rewrites a historical invoice.

`payments` (ULID, tenant-owned) has a unique `idempotency_key` (the idempotent-retry mechanism — see `SAAS_BILLING_ARCHITECTURE.md`) plus indexes on `(tenant_id, status)`, `subscription_id`, `gateway_payment_id`, and `gateway_order_id`. It never carries a gateway secret — only public-safe reference ids and an optional `gateway_signature` used solely for the verification comparison, never re-exposed via the API (`PaymentResource` omits it).

`webhook_events` (auto-increment id, platform-global — a webhook arrives with no authenticated tenant session, so this deliberately isn't tenant-scoped) is unique on `(gateway, gateway_event_id)`, the idempotency ledger that makes a duplicated/retried gateway webhook delivery a safe no-op.

Phase 12 adds `coupons`/`coupon_services`/`coupon_categories`/`coupon_usages`, `membership_plans`/`membership_plan_services`/`membership_plan_categories`/`customer_memberships`/`membership_payments`, and `loyalty_accounts`/`loyalty_transactions` — every one `BelongsToTenant` like every other tenant-owned table since Phase 1. `membership_payments` is its own table rather than a `payments` row, since `payments.subscription_id` is a required FK into the unrelated SaaS-subscription domain. `loyalty_transactions.unique(booking_id, type)` is the idempotency guarantee behind "a booking earns points at most once" — it works because NULL is never equal to NULL in a unique index, so `ADJUSTMENT`/`EXPIRE` rows (no associated booking) are unconstrained while a real booking-linked `EARN`/`REDEEM` row is deduplicated. Loyalty *configuration* is not a new table at all — it reuses the existing `salon_settings` key-value store via new `SalonSettingKey` cases. `bookings` gained an additive pricing-breakdown snapshot (`coupon_id`/`coupon_code`/`coupon_discount`, `customer_membership_id`/`membership_discount`, `loyalty_points_redeemed`/`loyalty_discount`/`loyalty_points_earned`) — the pre-existing `discount` column keeps its exact old meaning (the combined total) for backward compatibility. See `LOYALTY_MEMBERSHIP_COUPON_ARCHITECTURE.md`.

## Phase 13 — reporting indexes

No new tables — Phase 13's reports read exclusively from tables Phases 1–12 already created. Migration `2026_08_27_100200_add_reporting_indexes.php` adds five composite indexes for query patterns the existing indexes didn't cover: `booking_items(tenant_id, service_id)` (service/revenue-by-service `GROUP BY`), `customer_profiles(tenant_id, created_at)` (new-customer/growth-series range scans), `coupon_usages(tenant_id, used_at)` (the usage ledger's date-range filter), `customer_memberships(tenant_id, starts_at)` (membership-report date range — distinct from the existing `(tenant_id, status, expires_at)` index, which serves active-membership lookups, not this), and `loyalty_transactions(tenant_id, created_at)` / `(tenant_id, type)` (the loyalty ledger's date-range filter and per-type sums). See `REPORTING_ANALYTICS_ARCHITECTURE.md` for the full report architecture and the query patterns behind each index.

## Phase 14 — security/performance hardening

Migration `2026_08_27_100300_harden_loyalty_membership_fk_and_notification_index.php` (purely corrective, no data changes): (1) changes `customer_memberships.customer_id`, `loyalty_accounts.customer_id`, `loyalty_transactions.customer_id`, and `loyalty_transactions.loyalty_account_id` from `cascadeOnDelete()` to `restrictOnDelete()` — these four were created inconsistent with every sibling financial/historical table in their own migration (`coupon_usages.customer_id`/`membership_payments.customer_id` already used `restrictOnDelete()`), and a future hard-delete of a `Customer` row would otherwise have silently destroyed their loyalty ledger and membership history; (2) adds `notifications(user_id, created_at)`, the notification inbox's primary query shape, which no existing index covered. See `SECURITY_HARDENING.md`/`PERFORMANCE_HARDENING.md` for the full audit.
