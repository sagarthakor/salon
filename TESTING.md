# Testing

Run `php artisan test`. Phase 1 covers registration, login, logout, current-user access, tenant membership, authorization policy decisions, cross-tenant context rejection, and automatic tenant model scoping. Phase 2 adds salon/settings, branch CRUD, working-hour validation, holiday uniqueness, staff denial, and cross-tenant direct-ID tests. Tests use isolated SQLite databases through Laravel's default test configuration.

Phase 3 adds category/service CRUD, ownership, money/duration validation, filters, soft deletion, and direct-ID tenant-isolation tests.

Phase 4 adds staff CRUD and soft deletion, cross-branch service-assignment rejection, working-hour and break validation (invalid times, off-day breaks, overlaps), leave overlap validation, self-view-only staff authorization, customer denial, and cross-tenant direct-ID isolation across staff, breaks, and leave.

Phase 5 adds customer CRUD and soft deletion, validation, tenant-scoped duplicate-phone rejection (and same-phone-across-tenants acceptance), name/phone/email search, status/gender filters, owner-only notes and summary, staff read-only access, platform-customer denial, self-service profile view/update via `/customer/profile`, and cross-tenant direct-ID isolation across customers and notes.

Phase 6 adds the booking engine: full create-confirm-check_in-in_service-complete lifecycle with invalid-transition rejection; foreign/inactive-service and past-date rejection; specific-staff, any-available-staff, inactive-staff, and staff-cannot-perform-service rejection; sequential-same-staff and parallel-different-staff multi-service scheduling with duration/price totals; historical price-snapshot immutability after a service price change; availability exclusion by branch holiday, closed branch, staff break, staff leave, and existing-booking conflict (with fallback to another eligible staff member); booking-buffer enforcement (adjacent slot blocked, post-buffer slot allowed); maximum-advance-booking-window enforcement; owner-override vs. customer-window-respecting cancellation; reschedule revalidation rejecting a slot that became conflicted; staff's full operational access vs. platform-customer denial; and cross-tenant isolation (direct-ID access plus rejection of a booking naming another tenant's branch, customer, service, or staff). A dedicated concurrency test exercises the same lock-and-revalidate code path a real race would hit — see the "Concurrency test and its limitation" note in `BOOKING_ENGINE.md` for why PHPUnit cannot exercise genuine parallel requests.

A note on writing multi-tenant HTTP tests in this suite: `$this->actingAs()` and `$this->withHeader()` mutate the shared test-case instance and both return `$this`, so storing two "clients" from sequential `actingAs()` calls (e.g. `$apiA` then `$apiB`) does not give two independent actors — the later call silently becomes the active user for both variables. Existing tests avoid this either by using a single acting-as client per test (switching tenants via `withHeader()` on the same client) or by creating the second tenant's fixture data directly through Eloquent with `TenantContext::set()`/`clear()` rather than a second HTTP client; follow the same pattern rather than interleaving two stored `actingAs()` results.

A note on test-writing pitfalls specific to this file: `$this->actingAs($owner, 'sanctum')->withHeader(...)` mutates the shared PHPUnit test-case HTTP client rather than returning an isolated one — caching the result in a variable and switching `actingAs()` to a second tenant *before* using the first cached variable silently corrupts it into acting as the second tenant. Every multi-tenant test in this file completes one tenant's full request-then-assert sequence before ever calling `actingAs()` for the other, rather than pre-building two "client" variables and interleaving them.
