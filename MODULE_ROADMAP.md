# Module Roadmap

Phase 1 provides identity, tenancy, API conventions, and tests. Phase 2 provides salon profiles, database-backed settings, branches, working hours, and holidays. Phase 3 adds service categories and services (staff-service mapping deferred, since no staff table existed yet). Phase 4 adds staff profiles, branch and service assignment, working hours, breaks, and leave. Phase 5 adds tenant-scoped customer profiles, notes, and self-service profile access. Phase 6 adds the booking engine — availability/slot generation, item-level multi-staff bookings with price/duration snapshots, transactional double-booking prevention, and cancellation/reschedule with full revalidation — tying together services, staff schedules/breaks/leave, branches, and customers. Phase 7 adds the Flutter **customer** mobile app (Android + iOS, one codebase) — auth, salon/branch/service discovery, the full booking flow against the real availability/booking APIs, booking history, cancellation, rescheduling, and profile management — plus two small additive backend endpoints and one additive response field the mobile client genuinely needed (see `MOBILE_API_INTEGRATION.md`). Phase 8 extends the **same** Flutter codebase (never a second app) with a role-aware owner/admin surface — a real backend-derived dashboard (`GET /dashboard/summary`, new in this phase), full booking management (list/filter/details/status transitions/reschedule), staff management (CRUD + services + working hours + breaks + leave), service/category management, customer management (CRUD + notes + summary — the Phase 5 `CustomerController::summary` placeholder-zeros bug was fixed here with real booking-derived data), branch management, and salon/booking-settings management — all against the existing Phase 2–6 APIs plus the one new dashboard endpoint; role is read from the real `UserResource.role` value and only ever changes navigation, never backend authorization, which is independently enforced on every request regardless of which screen the app shows. See `OWNER_APP_ARCHITECTURE.md`. Phase 9 extends the same Flutter project a third time with a real staff app — a focused daily-workflow surface (today's appointments, my appointments, my schedule/services/leave view-only, my profile view-only) reusing the owner surface's `BookingRepository`/`StaffRepository`/screens wherever the backend already authorizes staff identically to an owner (booking transitions, viewing own schedule/services/leave), with exactly one new backend endpoint (`GET /staff/me`, resolving a staff member's own profile from their authenticated identity — never a client-supplied id). See `STAFF_APP_ARCHITECTURE.md`. Phase 10 makes the product a real SaaS: database-driven plans (default `SALON_BASIC`, ₹500.00/month, 14-day trial — never a hard-coded price anywhere), a per-tenant subscription with a real state machine (`trialing` → `active` → `past_due` → `grace_period` → `expired`, plus owner-initiated `cancel_at_period_end` → `cancelled`), a Razorpay integration hidden behind a `PaymentGatewayInterface` abstraction (server-verified payments and webhooks — never trusting a client-reported success or a client-supplied amount), real invoices with atomically-generated sequential numbers and price-at-billing-time snapshots, a daily scheduler for time-based lifecycle transitions, and an `EnsureActiveSubscription` middleware gating business features (never billing/renewal itself) on subscription standing — plus the matching owner-app Flutter screens (subscription status for all six states, plan selection, a server-authoritative payment flow, payment/invoice history). See `SAAS_BILLING_ARCHITECTURE.md`. Phase 11 adds the multi-channel notification system: in-app (a plain `notifications` table, deliberately not tenant-scoped since a customer's inbox spans every tenant they hold a profile with), push (Firebase Cloud Messaging HTTP v1, behind `PushProviderInterface`), email (Laravel's existing mail architecture), WhatsApp (official Meta Cloud API, template-only, behind `WhatsAppProviderInterface`), and SMS (abstraction only — no vendor selected yet, behind `SmsProviderInterface`) — all reached through one `NotificationDispatcher` that controllers/services never call a channel or provider around; booking and billing events fire the same plain domain events Phases 6/10 already established, now with a handful of additions (`BookingCheckedIn`/`BookingStarted`/`BookingNoShow`, `SubscriptionPastDue`/`SubscriptionGracePeriod`) for the transitions that had no event yet. Per-user and per-tenant channel preferences, idempotent 24h/2h booking reminders, queued+retried external delivery with full audit tracking (`notification_deliveries`), and device-token management round it out. See `NOTIFICATION_ARCHITECTURE.md`. Phase 12 adds coupons, paid customer memberships, and a loyalty points program, all converging on one `BookingPricingService` that `BookingService::create()` calls from inside its existing transaction — never a controller computing a discount. At most one primary discount applies per booking (an explicitly-supplied coupon beats an automatically-detected active membership benefit; never both), with loyalty-point redemption optionally stacking on top; every booking snapshots its own discount breakdown permanently, so a later coupon/plan change never rewrites history. Customer memberships get their own payment ledger (`membership_payments`) reusing the exact same `PaymentGatewayInterface` and webhook Phase 10 established — deliberately never conflated with the SaaS subscription domain, which is a completely different "owner pays platform" concept. Loyalty configuration extends the existing `salon_settings` key-value store (no new settings table), and loyalty earning reuses the existing `BookingCompleted` event (never a new one) with a race-safe, idempotent ledger. See `LOYALTY_MEMBERSHIP_COUPON_ARCHITECTURE.md`. Phase 13 adds reports and analytics — ten owner-only, server-aggregated report endpoints (dashboard/revenue/bookings/customers/services/staff/branches/coupons/memberships/loyalty) built entirely on real Phase 1–12 data, reached through a new `App\Services\Reports\*` class per report (never SQL in the controller) behind a shared `DateRange`/`ReportTimezoneResolver` pair that anchors every "today"/"this month" boundary to the salon's or a filtered branch's own timezone rather than the server's — a bug also fixed in Phase 8's `DashboardController::summary()`, which had it. Revenue/staff/service attribution reads `booking_items`' historical price snapshots and proportionally allocates each booking's discount across its items, so a later service-price or coupon-config change never rewrites a past report; coupon/membership/loyalty reports similarly read only from their respective immutable ledgers (`coupon_usages`, `loyalty_transactions`), never a model's current configuration or cached balance. The Flutter side is a new `Reports` section inside the existing Owner App, reached from the existing `More` tab, using `fl_chart` (the one new chart dependency this phase adds) purely to render backend-computed series — no aggregation happens client-side. See `REPORTING_ANALYTICS_ARCHITECTURE.md`. Phase 14 is a security + performance hardening pass across Phases 1–13, not a new feature phase: a full code audit found no CRITICAL/HIGH issues and fixed the real MEDIUM ones it did find — two MySQL-specific concurrency races invisible under the project's SQLite test suite (a booking staff-conflict check and a coupon per-customer usage check, both upgraded to locking reads), a webhook-idempotency gap that could permanently swallow a crashed delivery, checkout no longer holding a DB transaction open across the synchronous Razorpay call, a previously-absent general API rate limit, and a cascade-delete inconsistency on customer-linked loyalty/membership tables corrected to match the project's own established convention for protecting financial history. See `SECURITY_HARDENING.md` and `PERFORMANCE_HARDENING.md` for the full audit. Production deployment, infrastructure, store release, and production credentials are Phase 15 — not started. AI features follow only after their own dependent contracts are stable.
